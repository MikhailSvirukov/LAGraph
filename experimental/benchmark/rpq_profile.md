# Профилирование RPQ

Ветка `svmk17/rpq-paths-profiling`; исходная версия `783872fd`, отдельный
коммит AUTO `fa40ffd3`. Оба дескриптора умножения явно используют `GxB_DEFAULT`
(AUTO). Подготовка/транспонирование входов вызывающим кодом не входят в профиль.

## Запуск

Собрать LAGraph обычным способом. При запуске приложения, использующего эту
сборку, задать префикс файлов (каталог должен существовать):

```sh
mkdir -p /tmp/rpq-profile
LG_RPQ_PROFILE=/tmp/rpq-profile/run LG_RPQ_PROFILE_RUN_ID=experiment-1 ./your-benchmark
```

Каждый вызов публичного RPQ API создаёт отдельный файл
`run.<pid>.<call>.tsv` в исключительном режиме, без перезаписи существующего файла.
При повторном запуске используйте новый префикс/каталог. `RUN_ID` — необязательная
метка запуска; номер конкретного запроса алгоритму не передаётся. Для сопоставления
используйте PID и порядок вызовов, учитывая разогревы и повторения бенчмарка.

Без `LG_RPQ_PROFILE` дополнительные ожидания и обходы матриц отключены.
Ошибки открытия/записи профиля сообщаются в stderr и не меняют результат RPQ.
Файлы одного процесса не перемешиваются даже при параллельных вызовах.

## Агрегация без графиков

Скрипт требует только Python 3 и стандартную библиотеку:

```sh
python3 experimental/benchmark/rpq_profile.py '/tmp/rpq-profile/*.tsv' > queries.tsv
python3 experimental/benchmark/rpq_profile.py '/tmp/rpq-profile/*.tsv' --by iteration > iterations.tsv
python3 experimental/benchmark/rpq_profile.py '/tmp/rpq-profile/*.tsv' --by label > labels.tsv
python3 experimental/benchmark/rpq_profile.py '/tmp/rpq-profile/*.tsv' --by sample > samples.tsv
python3 experimental/benchmark/rpq_profile.py '/tmp/rpq-profile/*.tsv' --all > all.tsv
python3 experimental/benchmark/rpq_profile.py '/tmp/rpq-profile/*.tsv' --columns 'file,run_id,query.end.*,traverse.mxm*.total_ms.sum,reconstruct.final.*.last' > selected.tsv
```

По умолчанию одна строка на вызов с основными временами, ростом структур,
дубликатами и результатами. `--all` сохраняет все метрики в широком виде.
Для каждого числового поля доступны `.sum`, `.max`, `.last`; для текстовых —
`.last`. Суммировать нужно времена отдельных операций и счётчики итераций.
Счётчики восстановления накопительные: для них используйте `.last`, а для пиков
памяти по снимкам — `.max`. Суммы размеров матриц не означают объём памяти.
В режиме `--by iteration` метки агрегируются внутри итерации; `--by label`
сохраняет отдельную строку для каждой пары «итерация, метка».

`complete=1` означает наличие финального статуса вызова, включая завершение с
ошибкой. Смотрите также `query.end.status.last`. При аварии/таймауте завершённые
итерации и сброшенные снимки сохраняются, последняя незавершённая итерация может
отсутствовать. Скрипт пропускает оборванную последнюю строку с сообщением в stderr.

## Формат и точки измерений

TSV: `phase iteration label event elapsed_ms metric value`. Единицы времени —
миллисекунды, памяти — байты; количества — целые числа. `label=-1` означает
операцию вне цикла меток, `iteration=0` на первом этапе — подготовку.
`elapsed_ms` — время контрольной точки от начала вызова. Числовые значения
записываются без потери разрядов целочисленных счётчиков.

На первом этапе значения собираются после операций, буфер файла сбрасывается
после очистки каждой итерации. В записи итерации присутствуют:

- `begin`: входной frontier и старая P.
- `new_H`, `new_C`, `new_next_frontier`: отдельные времена создания матриц.
- `mxm1`: H для каждой метки; H перезаписывается, значения между метками не суммируются.
- `mxm2`: накопленная C после каждой активной метки, текущий временный пул.
- `products_done`: итоговая C и пул перед построением фронта.
- `front_union`: BOOL-фронт до удаления false; `front_select`: после.
- `P_merge`: новая P, выделенные блоки и распределение их размеров.
- `free_frontier`: освобождение старого фронта.
- `iteration_end`: счётчики работы за итерацию, её время и очистка.

Матрицы: `*_nvals`, `*_nonempty`, `*_records`, `*_records_max`,
`*_matrix_bytes`, `*_format`, `*_sparsity`, `*_chain_sum`, `*_chain_max`.
Для BOOL `records` равно числу true, для H — числу состояний внутри значений,
для C/P — числу троек с учётом ячейки назначения. Средний размер непустой
ячейки получается как `records/nonempty`; средняя цепочка — `chain_sum/nonempty`.
Неизменяющиеся матрицы повторно не сканируются после каждого действия: их
последний снимок остаётся действующим до следующей записи об изменении.

`format`: 0=CSR, 1=CSC; `sparsity`: 1=hypersparse, 2=sparse, 4=bitmap, 8=full.
Размеры N/A и их формат записываются при подготовке. Матрица H по-прежнему
умножается с транспонированием N через дескриптор; AUTO не убирает этот флаг.

`pool_bytes` учитывает все временные блоки, включая промежуточные результаты
слияний. `C_reachable_bytes` — только уникальные блоки, достижимые из текущей C.
Разность показывает объём временных блоков, не используемых текущим результатом.
`pool_slots - pool_records` — незаполненные места во всём пуле.
`C_snapshot_scratch_bytes` — дополнительный буфер снимка для подсчёта уникальных
указателей; это накладные расходы профилирования.

P: `P_owned_*` — все удерживаемые владельцем блоки; `P_new_*` — блоки текущей
итерации. `P_new_block_bucket_0..7`: [1], [2..4], [5..16], [17..64],
[65..256], [257..1024], [1025..4096], [4097..∞] записей в новом блоке.
Блок выделяется точно под новые тройки, заголовки учитываются в байтах.

Для успешной итерации:

```text
p_added_records = P_after.records - P_before.records
p_duplicate_records = C.records - p_added_records
```

Это дубликаты относительно старой P. `union_duplicates` считает отдельно
совпадения во время построения C; промежуточные объединения могут повторно
обрабатывать одну и ту же запись. `product_records` и `temp_records_written`
описывают выполненную работу, а не размер итоговой C. На ошибках выделения
счётчики производства/записи могут включать попытки, не вошедшие в результат.
`front_*` и `merge_*` разделяют проверки принадлежности, быстрые отказы Bloom,
точные нахождения, ложноположительные ответы Bloom, просмотренные блоки и сравнения.
Слияние P делает два прохода, поэтому число проверок не равно числу входных троек.

На втором этапе снимки накопительные: примерно раз в 100 мс при достижении
безопасной точки (проверка через каждые 4096 обработанных пар/загруженных ячеек),
плюс обязательный `final` перед освобождением memo-структур. Это не таймерная
гарантия: одна долгая операция может задержать следующий снимок.

Записываются пары «зависимость–префикс», вызовы/глубина Propagate, возвраты по
active, отказы по семантике/длине/shortest, новые и повторные префиксы,
попытки/дубликаты публикации, длины опубликованных путей, время первого ответа
от начала вызова, размеры memo/зависимостей/путей/результатов/таблиц,
операции переключения активного префикса и очереди подготовки/расстояний.
`answers_before_filter` учитывает публикации до финального фильтра shortest;
`answers` и финальное `query.end.paths` отражают оставшиеся пути.
`count_limit=1` означает остановку выдачи по ограничению; `reject_length` —
отсечённые продолжения. Байты восстановленных узлов включают и промежуточные
префиксы, не попавшие в ответ. Память аллокатора и рабочие буферы GraphBLAS внутри
операции не учитываются; размеры снимков не являются точным пиком RSS.

## Интерпретация времени

У каждой операции первого этапа есть `call_ms`, `wait_ms`, `total_ms`.
Материализация явно завершается перед снимком, поэтому отложенная работа не
попадает в подсчёт размера следующей матрицы. Создание пустой матрицы не включает
все будущие выделения памяти её результатами.

`iteration_ms` включает измерения и сбор статистики, но не последующий сброс
буфера файла. `snapshot_ms`/`snapshots_ms` показывают время обходов структур,
`io_ms` — накопленное время сбросов до финальной записи (сам финальный сброс
в него не входит). Форматирование строк и атомарные счётчики также имеют цену.
На втором этапе `prepare_ms` включает всю подготовку зависимостей и корней;
`join_ms`, `memo_ms` и `publish_ms` измеряют соответствующие действия при
распространении. Публикация уже сохранённых путей при смене цели входит в общее
время восстановления, но не в `publish_ms`. Вложенные времена не нужно складывать
с общим временем этапа.

Синхронизация, обходы матриц и атомарные счётчики меняют исполнение. Профиль
показывает поведение инструментированной версии; простое вычитание snapshot_ms
не восстанавливает исходное время бенчмарка. Для сравнения общей скорости
запускайте отдельно тот же AUTO-коммит без включённого профилирования.
